# Architecture Decision Records

ADR — короткие документы, фиксирующие архитектурные решения и их причины.
По одному файлу на решение, неизменяемые после принятия (если решение
пересматривается — новый ADR со ссылкой на старый со статусом
"Superseded").

## Когда писать ADR

- Выбор между несколькими технологиями (Postgres vs MySQL, GIN vs MeiliSearch)
- Выбор между несколькими подходами (Eloquent vs Doctrine, write-through vs write-behind)
- Любое решение, которое через 3 месяца "почему мы так сделали?"
- Любое нарушение собственных стандартов (с обоснованием)

## Когда НЕ писать ADR

- Тривиальные технические детали (имя класса, формат логов)
- Решения, легко обратимые без последствий

## Шаблон

Файл: `NNNN-kebab-case-title.md` (нумерация 4-значная, начиная с `0001`).

```markdown
# ADR-NNNN: <название решения>

- **Статус:** Proposed | Accepted | Superseded by ADR-XXXX | Deprecated
- **Дата:** YYYY-MM-DD
- **Контекст плана:** Фаза N, шаг N.M (ссылка на docs/PLAN.md)

## Контекст

В каком окружении и под какой задачей принимается решение. Какие
ограничения. Что уже зафиксировано в предыдущих ADR.

## Рассматриваемые варианты

### Вариант 1: <название>
- Плюсы:
- Минусы:

### Вариант 2: <название>
- Плюсы:
- Минусы:

### Вариант 3: <название>
- Плюсы:
- Минусы:

## Решение

Выбран вариант N.

## Обоснование

Почему именно этот вариант, через призму контекста и ограничений выше.

## Последствия

- Что станет проще
- Что станет сложнее
- Какие новые риски / зависимости появляются
- Когда стоит пересмотреть решение (триггер для нового ADR)

## Ссылки

- Документация
- Бенчмарки (если решение опиралось на цифры)
- Связанные ADR
```
