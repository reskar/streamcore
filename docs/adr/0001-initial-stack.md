# ADR-0001: Initial stack

- Status: Accepted
- Date: 2026-05-11

## Context

Нужно зафиксировать выбор основного стека: фреймворк, рантайм, БД, паттерны
архитектуры и тулинг качества кода. Проект — бэкенд стримингового сервиса,
ставлю себе задачи на оптимизацию (высокий RPS, кэширование, OLAP), поэтому
стек должен это поддерживать без подгонки в полпути.

## Decision

### Фреймворк — Laravel 13

Вместо Symfony. У меня глубокий опыт на Laravel, и переключаться на Symfony
ради "более взрослого вида" — это потерять 2-3 недели на знакомство без
понятной отдачи. Laravel 13 в Octane-режиме покрывает все нужные сценарии
производительности.

### Рантайм — Laravel Octane + FrankenPHP

FrankenPHP в worker mode. Альтернативы — RoadRunner (зрелый, больше прод-кейсов)
и Swoole (специфический, больше учить). FrankenPHP — самый "горячий" выбор
сейчас, на Caddy под капотом, поддерживает HTTP/3. Для пет-проекта подойдёт,
плюс в индустрии его активно осваивают. Классический FPM не рассматриваю —
покажет одинаково при высокой нагрузке, но не показывает работу с worker-моделью.

### Архитектура — Hexagonal + DDD-tactical

`src/Domain` (PHP-only, без Laravel), `src/Application` (use cases),
`app/Infrastructure` (адаптеры). Eloquent живёт строго в Infrastructure как
реализация репозитория. Контроль через Deptrac и Pest arch-тесты.

Альтернатива — "Laravel way" с моделями в контроллерах. Отбросил: для проекта,
где осмысленные домены (catalog, watch progress, manifests) — это будущая боль.

### Хранилища

- **PostgreSQL 16** — основное OLTP. JSONB, FTS, партиционирование, GIN-индексы.
- **Redis 7** — кэш, очереди (Horizon), session/rate limiting.
- **ClickHouse** — viewing analytics (отдельный профиль, OLAP).
- **MeiliSearch** — каталог с фасетным поиском, более лёгкий чем Elasticsearch.

MySQL не выбираю, потому что Postgres даёт богатые типы и FTS из коробки —
для каталога это в плюс.

### Качество кода

- **PHP 8.4** с обязательным `declare(strict_types=1)`
- **PHPStan max** + larastan + strict-rules + deprecation-rules
- **PHP-CS-Fixer** с пресетом PER-CS 2.0 (вместо Laravel Pint — точнее настройки)
- **Rector** с PHP 8.4 + Laravel 13 наборами
- **Pest 4** для тестов, включая arch-тесты
- **Deptrac** для жёстких архитектурных границ
- **CaptainHook** для pre-commit (cs-fixer) и commit-msg (Conventional Commits)

### TDD-дисциплина

Red → Green → Refactor строго, отдельными коммитами. Тесты пишутся ДО кода.
Quality gates в CI: cs + stan + rector + arch + tests. Все обязательны.

### Инфраструктура

Docker Compose для локальной разработки: app (FrankenPHP), postgres, redis.
ClickHouse и MeiliSearch добавятся когда дойду до соответствующих фич.

GitHub Actions для CI: тот же `composer ci` + `composer audit`.

## Consequences

**Плюсы:**
- Один знакомый фреймворк → больше времени на интересные задачи (оптимизация
  каталога, HLS-манифесты, ClickHouse) и меньше на изучение нового
- Hexagonal с первого дня → доменная логика остаётся чистой, тестируемой
- Жёсткий статанализ → ошибки ловятся локально, не уходят в репозиторий
- TDD → меньше регрессий, спокойнее рефакторить

**Минусы и риски:**
- Laravel Octane имеет специфические грабли (singleton state между запросами,
  утечки памяти в long-running воркерах) — выявятся при первой реальной фиче
- ClickHouse требует отдельной модели данных и пайплайна — добавит сложности
  когда дойдёт до viewing analytics
- Hexagonal с самого начала может ощущаться избыточным для простых фич — но
  это сознательный выбор в пользу позднего масштабирования

## Когда пересмотреть

- Octane оказывается узким местом для конкретного сценария → выделить
  отдельный ADR с альтернативой (RoadRunner) и бенчмарком
- Hexagonal-границы начинают мешать вместо того, чтобы помогать → отдельный
  ADR с послаблениями для конкретных слоёв
